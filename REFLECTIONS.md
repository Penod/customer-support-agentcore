**Design decision.** I made a point of not letting the LLM answer factual or numerical questions on its own. Anything about products, policies, or loyalty tiers has to come from `search_knowledge_base`, which pulls from a real Bedrock Knowledge Base instead of the model's training data. Same idea for the loyalty discount math: it runs through `calculate_loyalty_discount` in the AgentCore Code Interpreter, not the LLM doing arithmetic in its head. That adds a bit of latency, but in a customer support setting, a hallucinated return policy or a wrong discount is a much worse outcome than a slightly slower reply.

**Challenge.** The hardest bug I hit had nothing to do with the agent's actual logic. It came from the fact that the same file behaves differently depending on where it runs. Locally, `uv run main.py '{"prompt": ...}'` worked fine because the CLI path parses a JSON argument. But when `agentcore deploy` starts the container, it runs with no arguments at all, so the same `__main__` block needs to call `app.run()` instead, which is what actually starts the server the AgentCore Runtime checks for health. I had that commented out, and I'd also forgotten to import `sys`. The result was a "Runtime initialization time exceeded" error that gave no hint the problem was really just two small lines at the bottom of the file. It was a good reminder that testing locally doesn't tell you anything about whether your deployment entrypoint actually works.

**Extending for production.** Right now the agent trusts whatever it's told rather than verifying it against real data: the refund tool accepts an amount without checking it against the order it's refunding, and the discount calculation trusts whatever tier and points the customer states instead of pulling them from an account record. In production, I'd have the agent look these up from an actual orders/customers system rather than taking them as free-form input. I'd also tighten the IAM permissions I had to grant during deployment. The Knowledge Base and Memory roles are scoped to the exact resource, but I ended up giving the Browser tool a wildcard resource just to get it working, and that's not something I'd ship as-is. Beyond that, I'd add guardrails around what the agent can promise a customer, since it currently states refund amounts and delivery dates with full confidence even when a tool call has failed, plus a way to hand off to a human agent when the model is uncertain, rather than letting it improvise the way it did when the Knowledge Base call failed and it invented generic tier benefits instead of saying it couldn't verify them.
